# 인증 로그인 흐름 읽는 법

이 문서는 Dogether RN 프로젝트에서 로그인과 세션 저장 흐름을 읽기 위한 문서입니다.

이 프로젝트의 로그인은 단순히 "버튼을 누르면 메인으로 이동"이 아닙니다.

실제 흐름은 다음처럼 여러 층을 거칩니다.

```txt
OnboardingScreen
-> useOnboarding hook
-> React Query mutation
-> AuthUseCase
-> AuthRepository
-> API 또는 Mock
-> sessionStore.login()
-> MMKV 저장
-> /splash 이동
-> 앱 시작 판단
-> /start, /main, /review, /update 중 하나로 이동
```

처음에는 길어 보이지만, 역할을 나눠서 보면 꽤 깔끔합니다.

## 2. 전체 로그인 흐름

버튼을 누른 뒤 전체 흐름은 이렇습니다.

```txt
사용자가 로그인 버튼 탭
-> mutation.mutate()
-> mutationFn 실행
-> SDK 또는 mock payload 준비
-> AuthUseCase 호출
-> AuthRepository 호출
-> AuthSession 반환
-> onSuccess에서 sessionStore.login(data)
-> MMKV + Zustand에 세션 저장
-> OnboardingScreen의 mutate 옵션 onSuccess에서 router.replace('/splash')
-> SplashScreen이 세션을 hydrate
-> useLaunchFlowQuery가 다음 화면 계산
-> router.replace(...)
```

핵심은 이것입니다.

```txt
로그인 성공 후 바로 /main으로 가지 않는다.
/splash로 보내서 앱 시작 판단을 다시 태운다.
```

## 3. 지원하는 로그인 타입

파일:

```txt
src/models/auth.ts
```

코드:

```ts
export type LoginType = 'apple' | 'kakao' | 'demo';
```

현재 앱은 세 가지 로그인 타입을 모델로 가지고 있습니다.

| 타입 | 의미 |
| --- | --- |
| `demo` | 학습/개발용 데모 로그인 |
| `kakao` | 카카오 로그인 |
| `apple` | Apple 로그인 |

이 값은 세션에 저장됩니다.

```ts
loginType: LoginType;
```

## 4. AuthSession 모델

파일:

```txt
src/models/auth.ts
```

코드:

```ts
export type AuthSession = {
  accessToken: string;
  refreshToken?: string | null;
  userName: string;
  loginType: LoginType;
  appleUserIdentifier?: string | null;
  hasCompletedStartFlow: boolean;
};
```

`AuthSession`은 로그인 성공 후 앱이 기억해야 하는 세션 정보입니다.

| 필드 | 의미 |
| --- | --- |
| `accessToken` | API 요청에 붙일 인증 토큰 |
| `refreshToken` | 토큰 갱신용 토큰, 현재는 optional |
| `userName` | 화면에 보여줄 사용자 이름 |
| `loginType` | `demo`, `kakao`, `apple` 중 하나 |
| `appleUserIdentifier` | Apple 로그인 사용자 식별자 |
| `hasCompletedStartFlow` | 시작 그룹 생성/참여 플로우 완료 여부 |

중요한 값은 `hasCompletedStartFlow`입니다.

로그인 직후에는 이 값이 `false`입니다.

---

## 5. 로그인 직후 hasCompletedStartFlow가 false인 이유

로그인했다고 바로 서비스 이용 준비가 끝나는 것은 아닙니다.

Dogether는 로그인 후 그룹을 만들거나 참여해야 메인 플로우가 자연스럽습니다.

그래서 로그인 직후 세션은 이렇게 저장됩니다.

```txt
accessToken 있음
userName 있음
loginType 있음
hasCompletedStartFlow = false
```

이후 그룹 생성/참여를 마치고 완료 화면에서 홈으로 가면:

```txt
hasCompletedStartFlow = true
```

로 바뀝니다.

다만 현재 앱 시작 판단은 실제 가입 그룹 목록을 source of truth로 보고 있습니다.

그래도 이 값은 "사용자가 시작 플로우를 완료했다"는 세션성 플래그로 중요합니다.

## 6. OnboardingScreen의 역할

파일:

```txt
src/screens/onboarding/OnboardingScreen.tsx
```

이 화면은 로그인 버튼을 그리고, 버튼을 mutation에 연결합니다.

핵심 코드는 이런 형태입니다.

```tsx
onPress={() => demoLoginMutation.mutate(undefined, { onSuccess: () => router.replace('/splash') })}
```

카카오도 비슷합니다.

```tsx
onPress={() => kakaoLoginMutation.mutate(undefined, { onSuccess: () => router.replace('/splash') })}
```

Apple도 비슷합니다.

```tsx
onPress={() => appleLoginMutation.mutate(undefined, { onSuccess: () => router.replace('/splash') })}
```

읽는 법:

```txt
버튼을 누르면 mutation을 실행한다.
mutation이 성공하면 /splash로 이동한다.
```

## 7. 왜 router.replace('/splash')를 쓸까?

`replace`는 현재 화면을 새 화면으로 교체합니다.

로그인 성공 후 온보딩으로 뒤로가기 할 수 있으면 이상합니다.

그래서:

```ts
router.replace('/splash')
```

를 씁니다.

또 `/main`으로 바로 가지 않고 `/splash`로 가는 이유는 다음 화면 판단을 한곳에서 통일하기 위해서입니다.

```txt
로그인 후
-> 강제 업데이트가 필요한지
-> 그룹이 있는지
-> 리뷰할 인증이 있는지
-> 메인으로 가도 되는지
```

이 판단은 `SplashScreen` + `AppLaunchUseCase`가 담당합니다.

파일:

## 10. useOnboarding의 의존성 준비

코드:

```ts
const loginStore = useSessionStore((state) => state.login);
const authUseCase = useMemo(() => new AuthUseCase(createAuthRepository()), []);
const [loginError, setLoginError] = useState<AppError | null>(null);
```

각 값의 의미:

| 값 | 의미 |
| --- | --- |
| `loginStore` | Zustand 세션 store의 login action |
| `authUseCase` | 로그인 usecase |
| `loginError` | 화면에 보여줄 로그인 에러 |
| `isAppleLoginAvailable` | Apple 로그인 버튼 표시 가능 여부 |
| `isKakaoLoginAvailable` | Kakao 로그인 버튼 표시 가능 여부 |

## 12. 로그인 가능 여부 체크

파일:

```txt
src/hooks/useOnboarding.ts
```

코드:

```ts
useEffect(() => {
  if (env.useMockAuth) {
    setIsAppleLoginAvailable(env.enableAppleSignIn);
    setIsKakaoLoginAvailable(true);
    return;
  }

  let mounted = true;
  setIsKakaoLoginAvailable(Platform.OS === 'ios' || Platform.OS === 'android');

  if (!env.enableAppleSignIn) {
    setIsAppleLoginAvailable(false);
    return () => {
      mounted = false;
    };
  }

  AppleAuthentication.isAvailableAsync()
    .then((available) => {
      if (!mounted) {
        return;
      }

      setIsAppleLoginAvailable(available);
    })
    .catch(() => {
      if (!mounted) {
        return;
      }

      setIsAppleLoginAvailable(false);
    });

  return () => {
    mounted = false;
  };
}, []);
```

이 effect는 화면이 나타난 뒤 Apple/Kakao 로그인을 사용할 수 있는지 확인합니다.

## 13. mock auth일 때 로그인 가능 여부

```ts
if (env.useMockAuth) {
  setIsAppleLoginAvailable(env.enableAppleSignIn);
  setIsKakaoLoginAvailable(true);
  return;
}
```

mock auth에서는 실제 Kakao SDK를 쓰지 않으므로 카카오 로그인을 가능하게 둡니다.

Apple은 `env.enableAppleSignIn`을 따릅니다.

즉 mock auth에서도 Apple 버튼은 환경 설정에 따라 숨길 수 있습니다.

## 14. 실제 auth일 때 로그인 가능 여부

실제 auth에서는 플랫폼과 native 기능을 봅니다.

```ts
setIsKakaoLoginAvailable(Platform.OS === 'ios' || Platform.OS === 'android');
```

카카오는 iOS/Android에서 가능하게 봅니다.

Apple은 먼저 설정값을 봅니다.

```ts
if (!env.enableAppleSignIn) {
  setIsAppleLoginAvailable(false);
  return;
}
```

그 다음 실제 기기/환경에서 가능한지 확인합니다.

```ts
AppleAuthentication.isAvailableAsync()
```

## 19. Kakao 이름 fallback

Kakao profile에서 이름이 비어 있을 수 있습니다.

그래서 helper가 있습니다.

```ts
function toKakaoDisplayName(profile: KakaoProfile) {
  const normalizedName = profile.name?.trim();
  if (normalizedName) {
    return normalizedName;
  }

  const normalizedNickname = profile.nickname?.trim();
  if (normalizedNickname) {
    return normalizedNickname;
  }

  const normalizedEmail = profile.email?.trim();
  if (normalizedEmail) {
    return normalizedEmail.split('@')[0] || normalizedEmail;
  }

  return 'Kakao User';
}
```

우선순위:

```txt
name
-> nickname
-> email 앞부분
-> "Kakao User"
```

서버와 화면에는 되도록 표시 가능한 이름을 넘기려는 의도입니다.

## 20. Apple 로그인 mutation

코드 구조:

```ts
const appleLoginMutation = useMutation({
  mutationFn: async () => {
    if (env.useMockAuth) {
      return authUseCase.loginWithApple({
        providerId: 'mock-apple-token-' + Date.now(),
        name: 'Apple User',
        authorizationCode: 'mock-authorization-code-' + Date.now(),
        appleUserIdentifier: 'mock-apple-user-' + Date.now(),
      });
    }

    const isAvailable = await AppleAuthentication.isAvailableAsync();
    if (!isAvailable) {
      throw getAppError('ATF-0004');
    }

    const credential = await AppleAuthentication.signInAsync({
      requestedScopes: [
        AppleAuthentication.AppleAuthenticationScope.FULL_NAME,
        AppleAuthentication.AppleAuthenticationScope.EMAIL,
      ],
    });

    if (!credential.identityToken || !credential.authorizationCode) {
      throw getAppError('ATF-0003');
    }

    return authUseCase.loginWithApple({
      providerId: credential.identityToken,
      name: toFallbackDisplayName(credential.fullName, credential.email),
      authorizationCode: credential.authorizationCode,
      appleUserIdentifier: credential.user,
    });
  },
  onSuccess: (data) => {
    loginStore(data);
  },
  onError: ...
});
```

Apple 실제 로그인 흐름:

```txt
Apple 버튼 탭
-> AppleAuthentication.isAvailableAsync()
-> AppleAuthentication.signInAsync()
-> identityToken/authorizationCode 검사
-> name fallback 계산
-> AuthUseCase.loginWithApple()
-> AuthRepository.loginWithApple()
-> AuthSession 반환
-> sessionStore.login()
```

## 22. Apple 이름 fallback

Apple은 최초 로그인 이후 이름/이메일을 다시 주지 않을 수 있습니다.

그래서 fallback을 둡니다.

```ts
function toFallbackDisplayName(fullName, email) {
  const displayName = toDisplayName(fullName);
  if (displayName) {
    return displayName;
  }

  if (email) {
    return email.split('@')[0] || 'Apple User';
  }

  return 'Apple User';
}
```

우선순위:

```txt
Apple fullName
-> email 앞부분
-> "Apple User"
```

## 24. AuthRepository contract

파일:

```ts
export interface AuthRepository {
```

## 53. 토큰 갱신 코드

AuthRepository contract에는 토큰 갱신 메서드가 있습니다.


```ts
async refreshSession(refreshToken: string): Promise<RefreshSessionPayload> {
  try {
    const response = await apiClient.post<
      ApiEnvelope<{ accessToken: string; refreshToken?: string | null }>
    >(endpoints.auth.refresh, { refreshToken });

    return {
      accessToken: response.data.data?.accessToken ?? '',
      refreshToken: response.data.data?.refreshToken ?? refreshToken,
    };
  } catch (error) {
    throw toAppError(error);
  }
}
```

현재 문서 기준으로는 로그인 흐름에서 주로 사용하지 않지만, 인증 구조 안에 준비되어 있습니다.

```txt
-> authUseCase.loginWithApple(...)
-> AuthRepositoryImpl.loginWithApple()
-> loginWithProvider({ providerLoginType: 'APPLE', appLoginType: 'apple', ... })
-> apiClient.post(endpoints.auth.login, ...)
-> AuthSession
-> sessionStore.login()
-> /splash
```

Apple mock 로그인:

```txt
env.useMockAuth true
-> mock token/code/user 생성
-> MockAuthRepository.loginWithApple()
-> mock AuthSession
-> sessionStore.login()
-> /splash
```

## 57. 초보자가 자주 헷갈리는 부분

### 57-1. 로그인 성공하면 왜 바로 main으로 안 가나?

앱 시작 판단을 통일하기 위해서입니다.

로그인 후에도 업데이트, 그룹 가입 여부, 리뷰 대기 여부를 확인해야 합니다.

그래서 `/splash`를 거칩니다.

### 57-2. AuthSession은 서버 응답 그대로인가?

아닙니다.

서버 응답을 repository에서 앱 내부 세션 모델로 변환한 것입니다.

### 57-3. mock 로그인도 세션 저장을 하나?

합니다.

mock repository도 `AuthSession`을 반환하고, 이후 `sessionStore.login()` 흐름은 실제 로그인과 같습니다.

### 57-4. 사용자가 로그인 창을 닫으면 에러 모달이 뜨나?

대부분 뜨지 않습니다.

Kakao/Apple 에러 변환 함수에서 취소는 `null`로 처리합니다.

### 57-5. accessToken은 어디에 저장되나?

`sessionStore.login()`이 `saveSession()`을 호출하고, `saveSession()`이 MMKV에 저장합니다.

### 57-6. API 요청은 Zustand의 token을 직접 쓰나?

아닙니다.

`apiClient`가 요청 직전에 MMKV에서 accessToken을 직접 읽어 Authorization header에 붙입니다.

## 61. 마지막으로 한 번에 정리

인증/로그인 흐름의 핵심은 이것입니다.

```txt
OnboardingScreen은 버튼과 이동을 담당한다.
useOnboarding은 SDK 호출, mutation, 에러 처리를 담당한다.
AuthUseCase는 AuthRepository를 감싼다.
createAuthRepository가 mock/API 구현체를 고른다.
AuthRepository는 AuthSession을 반환한다.
sessionStore.login은 AuthSession을 MMKV와 Zustand에 저장한다.
로그인 성공 후 /splash로 이동한다.
Splash/AppLaunchUseCase가 업데이트, 로그인 여부, 그룹 여부, 리뷰 여부를 보고 최종 화면을 정한다.
```

한 줄로 줄이면:

```txt
Dogether RN의 로그인은 "세션을 만들고 저장한 뒤, splash에서 앱 시작 판단을 다시 태우는 흐름"이다.
```
