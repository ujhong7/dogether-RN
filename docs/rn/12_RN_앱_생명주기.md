# React Native 앱 생명주기

이 문서는 Dogether RN 앱이 켜진 뒤 어떤 순서로 초기화되고 첫 화면이 결정되는지 설명합니다.

iOS의 `AppDelegate`, `SceneDelegate`, rootViewController, launch coordinator와 비교해서 React Native + Expo Router 앱의 시작 흐름을 이해하는 것이 목표입니다.

## iOS와 RN의 큰 차이

iOS에서는 앱 전체 생명주기를 주로 아래 객체에서 다룹니다.

| iOS | 역할 |
| --- | --- |
| `AppDelegate` | 앱 프로세스 시작, SDK 초기화, push, app-level event |
| `SceneDelegate` | window/scene 생성, rootViewController 연결 |
| `UIViewController` | 화면 단위 생명주기 |
| Coordinator | 첫 화면 결정, 화면 전환 |

React Native + Expo Router에서는 역할이 이렇게 나뉩니다.

| RN / Expo | iOS에 빗대면 | 역할 |
| --- | --- | --- |
| `package.json`의 `main` | 앱 진입점 설정 | 어떤 entry를 실행할지 결정 |
| `expo-router/entry` | root bootstrap | Expo Router 앱 시작 |
| `app/_layout.tsx` | root container / navigation controller | Provider, Stack, StatusBar 설정 |
| `app/index.tsx` | 초기 route | `/` 진입 시 `/splash`로 연결 |
| `SplashScreen` | launch screen + launch coordinator 일부 | 세션 복원, 첫 화면 분기 |
| `AppLaunchUseCase` | launch coordinator | update/onboarding/start/review/main 결정 |
| `useEffect` | 화면 생명주기 일부 | mount 후 작업, route 이동 |
| React Query | async state manager | 앱 시작 조건 비동기 계산 |
| Zustand store | app state store | 세션, 선택 그룹 등 앱 상태 |

## 실제 앱 진입점

Dogether RN의 `package.json`에는 이렇게 되어 있습니다.

```json
{
  "main": "expo-router/entry"
}
```

즉 이 프로젝트에서 실제 앱 진입점은 `App.tsx`가 아니라 `expo-router/entry`입니다.

`App.tsx` 파일은 Expo 기본 템플릿의 흔적으로 남아 있지만, Expo Router를 사용할 때는 보통 직접 실행되지 않습니다.

```text
package.json main
  -> expo-router/entry
  -> app/_layout.tsx
  -> app/index.tsx
  -> /splash
```

## `index.ts`는 왜 있나?

루트에 `index.ts`도 있습니다.

```ts
import { registerRootComponent } from 'expo';

import App from './App';

registerRootComponent(App);
```

이 파일은 Expo 기본 앱 진입 방식에서 쓰이는 형태입니다. 하지만 현재 `package.json`의 `main`이 `expo-router/entry`이므로, 실제 앱 화면 흐름을 읽을 때는 `app/_layout.tsx`부터 보는 것이 더 중요합니다.

처음 읽을 때 헷갈리지 않으려면 이렇게 기억하면 됩니다.

```text
Expo Router 프로젝트에서는
App.tsx보다 app/_layout.tsx와 app/index.tsx를 먼저 본다.
```

## 앱 시작 전체 흐름

Dogether RN 앱 시작 흐름은 다음과 같습니다.

```text
앱 실행
  -> expo-router/entry
  -> app/_layout.tsx
  -> QueryClientProvider
  -> Stack route 등록
  -> app/index.tsx
  -> Redirect /splash
  -> SplashScreen
  -> sessionStore.hydrate()
  -> useLaunchFlowQuery()
  -> AppLaunchUseCase.decideNextRoute()
  -> router.replace(...)
```

이 흐름은 iOS에서 앱이 켜진 뒤 root coordinator가 첫 화면을 고르는 구조와 비슷합니다.

## `_layout.tsx`: 앱의 root container

`app/_layout.tsx`는 앱 전체 route가 공통으로 거치는 부모 레이아웃입니다.

```tsx
export default function RootLayout() {
  return (
    <QueryClientProvider client={queryClient}>
      <StatusBar style="light" />
      <Stack screenOptions={{ headerShown: false }}>
        <Stack.Screen name="index" />
        <Stack.Screen name="splash" />
        <Stack.Screen name="onboarding" />
        <Stack.Screen name="main" />
      </Stack>
    </QueryClientProvider>
  );
}
```

역할:

| 요소 | 역할 |
| --- | --- |
| `QueryClientProvider` | React Query cache를 앱 전체에서 공유 |
| `StatusBar` | 앱 전체 상태바 스타일 |
| `Stack` | 화면을 stack 방식으로 관리 |
| `Stack.Screen` | route 목록과 화면 옵션 등록 |

iOS로 비유하면 `UINavigationController`를 만들고, 앱 전체 의존성을 주입하는 root container에 가깝습니다.

## `app/index.tsx`: 루트 route

`app/index.tsx`는 `/` route입니다.

```tsx
export default function Index() {
  return <Redirect href="/splash" />;
}
```

뜻:

```text
/ 로 들어오면 화면을 그리지 않고 /splash로 보낸다.
```

즉 Dogether RN은 앱 루트에서 바로 스플래시로 이동한 뒤, 스플래시에서 실제 첫 화면을 결정합니다.

## SplashScreen의 역할

`SplashScreen`은 앱 시작 조건을 확인하고 첫 화면을 결정합니다.

담당:

- MMKV에 저장된 세션을 Zustand store로 복원
- launch-flow query 실행
- 강제 업데이트 여부 확인
- 로그인 여부 확인
- 참여 그룹 여부 확인
- 대기 리뷰 여부 확인
- 결과에 따라 route 교체

흐름:

```text
SplashScreen
  -> hydrate()
  -> useLaunchFlowQuery()
  -> data가 나오면 router.replace(...)
```

## 세션 hydrate

앱이 켜지면 먼저 저장소에 남아 있는 세션을 복원해야 합니다.

`SplashScreen`:

```tsx
const hydrate = useSessionStore((state) => state.hydrate);

useEffect(() => {
  hydrate();
}, [hydrate]);
```

`sessionStore`:

```ts
hydrate: () => {
  const session = readSession();
  if (!session) {
    set({
      hydrated: true,
      accessToken: null,
      ...
    });
    return;
  }

  set({
    hydrated: true,
    accessToken: session.accessToken,
    ...
  });
}
```

읽는 법:

```text
SplashScreen mount
  -> hydrate 호출
  -> MMKV에서 세션 읽기
  -> 세션이 있으면 Zustand에 복원
  -> 세션이 없으면 비로그인 상태로 설정
  -> hydrated true
```

## hydrated가 중요한 이유

`hydrated`는 저장소에서 세션을 다 읽었는지 나타냅니다.

```text
hydrated === false
  -> 아직 로그인 여부를 알 수 없음

hydrated === true
  -> 세션 복원 완료. 로그인 여부 판단 가능
```

앱 시작 직후에는 access token이 null이어도, 아직 저장소를 읽기 전일 수 있습니다.

그래서 `useLaunchFlowQuery`는 `hydrated`가 true가 되기 전까지 실행되지 않습니다.

```tsx
return useQuery({
  queryKey: ['launch-flow', hydrated, token],
  enabled: hydrated,
  queryFn: async () => {
    await useCase.launchDelay();
    return useCase.decideNextRoute(Boolean(token), env.appVersion);
  },
});
```

## useLaunchFlowQuery

`useLaunchFlowQuery`는 앱 시작 판단을 React Query로 실행합니다.

```text
useLaunchFlowQuery
  -> sessionStore.hydrated 읽기
  -> sessionStore.accessToken 읽기
  -> AppLaunchUseCase 생성
  -> hydrated일 때만 query 실행
  -> 다음 route 반환
```

`queryKey`에 `hydrated`와 `token`이 들어갑니다.

```tsx
queryKey: ['launch-flow', hydrated, token]
```

이 뜻은 세션 복원 상태나 토큰이 바뀌면 앱 시작 판단도 다시 계산해야 한다는 것입니다.

## AppLaunchUseCase

첫 화면 판단은 `AppLaunchUseCase`가 담당합니다.

```ts
export type LaunchRoute = 'update' | 'onboarding' | 'start' | 'main' | 'review';
```

분기 순서:

```text
1. 강제 업데이트가 필요하면 update
2. 로그인 세션이 없으면 onboarding
3. 참여한 그룹이 없으면 start
4. 대기 리뷰가 있으면 review
5. 그 외에는 main
```

실제 흐름:

```text
AppLaunchUseCase.decideNextRoute(isLoggedIn, appVersion)
  -> appInfoRepository.checkForceUpdate(appVersion)
  -> if forceUpdate return update
  -> if !isLoggedIn return onboarding
  -> groupRepository.getGroups()
  -> if groups.length === 0 return start
  -> reviewRepository.getPendingReviews()
  -> if pendingReviews.length > 0 return review
  -> return main
```

## route 교체

`SplashScreen`은 launch-flow 결과에 따라 `router.replace`를 호출합니다.

```tsx
if (data === 'update') {
  router.replace('/update');
  return;
}

if (data === 'review') {
  router.replace('/review');
  return;
}

if (data === 'onboarding') {
  router.replace('/onboarding');
  return;
}

if (data === 'start') {
  router.replace('/start');
  return;
}

router.replace('/main');
```

`replace`를 쓰는 이유:

```text
첫 화면 결정 후 사용자가 뒤로가기로 splash에 돌아오면 안 되기 때문
```

## 첫 화면 결정 표

| 조건 | 이동 route |
| --- | --- |
| 강제 업데이트 필요 | `/update` |
| 로그인 세션 없음 | `/onboarding` |
| 가입한 그룹 없음 | `/start` |
| 처리할 리뷰 있음 | `/review` |
| 일반 정상 진입 | `/main` |

이 표가 Dogether RN 앱 시작 생명주기의 핵심입니다.

## 로그인 후 왜 splash로 돌아가나?

온보딩에서 로그인에 성공하면 바로 `/main`으로 가지 않고 `/splash`로 이동합니다.

```tsx
router.replace('/splash');
```

이유:

```text
로그인 성공
  -> 세션 저장
  -> splash로 이동
  -> 앱 시작 조건 다시 판단
  -> 그룹 없음이면 start
  -> 리뷰 있으면 review
  -> 아니면 main
```

스플래시가 launch coordinator 역할을 하기 때문입니다.

## 앱 시작과 환경값

앱 실행 환경은 `src/config/env.ts`에서 읽습니다.

`package.json` 스크립트는 `EXPO_PUBLIC_*` 값을 주입합니다.

```bash
npm run start:mock
npm run start:dev
npm run start:prod
```

앱 시작 판단에서도 환경값을 씁니다.

```tsx
return useCase.decideNextRoute(Boolean(token), env.appVersion);
```

Repository factory도 env 값을 보고 API/Mock 구현체를 선택합니다.

```text
env.useMockGroups
  -> MockGroupRepository or GroupRepositoryImpl
```

따라서 앱 생명주기를 읽을 때는 `package.json -> env.ts -> repositories/index.ts`도 함께 보면 좋습니다.

## 앱 foreground/background 생명주기

React Native에서는 앱이 foreground/background로 이동하는 상태를 `AppState`로 감지할 수 있습니다.

예시:

```tsx
import { AppState } from 'react-native';

useEffect(() => {
  const subscription = AppState.addEventListener('change', (state) => {
    if (state === 'active') {
      // 앱이 foreground로 돌아옴
    }

    if (state === 'background') {
      // 앱이 background로 내려감
    }
  });

  return () => subscription.remove();
}, []);
```

Dogether RN에는 현재 앱 전체 foreground/background를 직접 감지하는 코드는 없습니다.

필요해질 수 있는 경우:

- 앱 복귀 시 프로필/투두 재조회
- 백그라운드 진입 시 draft 저장
- 토큰 갱신
- 푸시 알림 처리

## 화면 생명주기와 앱 생명주기 구분

앱 생명주기와 화면 생명주기는 다릅니다.

| 구분 | 의미 | RN에서 주로 보는 위치 |
| --- | --- | --- |
| 앱 생명주기 | 앱 실행, foreground/background | `AppState`, root layout |
| 앱 시작 분기 | 첫 화면 결정 | `SplashScreen`, `AppLaunchUseCase` |
| 화면 생명주기 | 화면 mount/unmount, focus/blur | `useEffect`, `useFocusEffect` |

이 문서는 앱 시작 분기에 집중합니다. 화면 단위 생명주기는 별도 문서에서 더 자세히 봅니다.

## 에러가 나면 어떻게 되나?

앱 시작 판단 중 API 에러가 날 수 있습니다.

`SplashScreen`은 `useLaunchFlowQuery`의 에러를 확인합니다.

```tsx
if (isError) {
  const appError = toAppError(error);
  ...
}
```

에러 종류에 따라:

```text
alert variant
  -> AppAlertModal 표시
  -> 닫으면 logout 후 /onboarding

fullScreen variant
  -> FullScreenErrorState 표시
  -> 다시 시도 버튼에서 refetch()
```

즉 앱 시작 실패도 공통 에러 UI 흐름을 따릅니다.

## 앱 생명주기 읽는 순서

처음 코드를 따라갈 때는 아래 순서로 읽으면 됩니다.

```text
1. package.json
   -> main이 expo-router/entry인지 확인

2. app/_layout.tsx
   -> QueryClientProvider, Stack, StatusBar 확인

3. app/index.tsx
   -> / 에서 /splash로 Redirect 확인

4. app/splash.tsx
   -> /splash route가 SplashScreen에 연결되는지 확인

5. src/screens/splash/SplashScreen.tsx
   -> hydrate, launch query, router.replace 확인

6. src/stores/sessionStore.ts
   -> hydrate/login/logout과 hydrated 의미 확인

7. src/lib/storage/sessionStorage.ts
   -> MMKV에서 세션을 어떻게 읽고 쓰는지 확인

8. src/queries/useLaunchFlowQuery.ts
   -> enabled: hydrated와 queryKey 확인

9. src/services/usecases/appLaunchUseCase.ts
   -> 첫 화면 결정 조건 확인

10. src/services/repositories/index.ts
    -> API/Mock repository 선택 확인
```

## iOS와 RN 앱 시작 대조표

| iOS 개념 | RN / Expo Router | Dogether RN 예시 |
| --- | --- | --- |
| 앱 entry 설정 | `package.json main` | `expo-router/entry` |
| root container | `app/_layout.tsx` | `QueryClientProvider`, `Stack` |
| root route | `app/index.tsx` | `Redirect /splash` |
| launch screen/coordinator | `SplashScreen` | 세션 복원, route 분기 |
| local session restore | MMKV + Zustand hydrate | `sessionStore.hydrate()` |
| async launch decision | React Query | `useLaunchFlowQuery()` |
| launch business rules | UseCase | `AppLaunchUseCase` |
| root navigation change | `router.replace` | `/update`, `/onboarding`, `/start`, `/review`, `/main` |
| foreground/background | `AppState` | 현재 직접 사용 없음 |

## 자주 헷갈리는 점

### App.tsx가 시작점 아닌가?

현재 프로젝트에서는 `package.json`의 `main`이 `expo-router/entry`입니다. 앱 흐름은 `app/_layout.tsx`와 `app/index.tsx`부터 보면 됩니다.

### 왜 SplashScreen에서 세션을 복원하나?

첫 화면을 결정하려면 로그인 여부가 필요합니다. 로그인 여부는 MMKV에 저장된 세션을 읽어야 알 수 있으므로, 스플래시에서 먼저 hydrate합니다.

### hydrated와 accessToken은 뭐가 다른가?

```text
hydrated -> 저장소 읽기가 끝났는가
accessToken -> 로그인 토큰이 있는가
```

`hydrated`가 false이면 accessToken이 null이어도 아직 로그아웃이라고 판단하면 안 됩니다.

### 왜 첫 화면 이동에 replace를 쓰나?

스플래시는 중간 판단 화면입니다. 사용자가 뒤로가기로 다시 돌아오면 안 되므로 `replace`를 씁니다.

### 앱 foreground/background 처리는 어디 있나?

현재는 직접 처리하지 않습니다. 필요하면 React Native의 `AppState`를 사용합니다.

## 한 줄 요약

```text
Dogether RN의 앱 생명주기는
expo-router/entry에서 시작해 app/_layout.tsx로 root Stack을 만들고,
app/index.tsx가 /splash로 보내며,
SplashScreen이 세션을 hydrate한 뒤 AppLaunchUseCase로 첫 화면을 결정하고,
router.replace로 update/onboarding/start/review/main 중 하나로 이동하는 흐름이다.
```
