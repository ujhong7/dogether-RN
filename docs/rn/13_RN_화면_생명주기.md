# React Native 화면 생명주기

이 문서는 Dogether RN 프로젝트에서 화면 하나가 나타나고, 상태를 준비하고, 데이터를 불러오고, 포커스되고, 사라지는 흐름을 설명합니다.

앱 전체 생명주기가 `expo-router/entry -> _layout -> splash -> 첫 화면` 흐름이라면, 화면 생명주기는 각 `Screen` 컴포넌트 안에서 일어나는 `render`, `useEffect`, `useFocusEffect`, `React Query`, `cleanup` 흐름입니다.

## iOS와 RN 화면 생명주기 비교

iOS UIKit에서는 화면 생명주기를 주로 `UIViewController` 메서드로 이해합니다.

| iOS | 의미 |
| --- | --- |
| `viewDidLoad` | view가 처음 로드됨 |
| `viewWillAppear` | 화면이 곧 나타남 |
| `viewDidAppear` | 화면이 나타남 |
| `viewWillDisappear` | 화면이 곧 사라짐 |
| `viewDidDisappear` | 화면이 사라짐 |
| `deinit` | 객체 해제 |

React Native 함수형 컴포넌트에서는 아래 개념으로 나눠 봅니다.

| RN / React | iOS에 빗대면 | 역할 |
| --- | --- | --- |
| 컴포넌트 함수 실행 | `view`를 현재 state로 다시 구성 | JSX 반환 |
| `useState` | view controller local state | 화면 내부 상태 |
| `useEffect(..., [])` | `viewDidLoad`에 가까움 | mount 후 1회 작업 |
| `useEffect(..., [deps])` | 특정 값 변화 감지 | deps 변경 시 작업 |
| effect cleanup | `deinit`, observer remove | timer/listener/task 정리 |
| `useFocusEffect` | `viewWillAppear/viewWillDisappear` | 화면 focus/blur 대응 |
| React Query | async loading state | 서버 데이터 로딩/캐시 |
| `router.push/replace/back` | navigation | 화면 전환 |

완전히 1:1 대응은 아니지만, iOS 개발자가 처음 읽을 때는 이 표로 감을 잡으면 됩니다.

## 화면이 나타나는 큰 흐름

Expo Router에서 화면 하나가 보이는 흐름은 다음과 같습니다.

```text
router.push('/main') 또는 Stack route 선택
  -> app/main.tsx
  -> MainScreen 컴포넌트 실행
  -> Hook 호출
  -> JSX 반환
  -> React Native가 native view로 반영
  -> useEffect 실행
  -> React Query 비동기 결과 도착
  -> 상태 변경
  -> 컴포넌트 재렌더링
```

중요한 점:

```text
컴포넌트 함수는 한 번만 실행되는 초기화 함수가 아니다.
state/query/store가 바뀌면 다시 실행될 수 있다.
```

## render는 자주 일어난다

React Native의 Screen 함수는 상태가 바뀔 때마다 다시 실행될 수 있습니다.

```tsx
export function MainScreen() {
  const { currentGroup, filteredTodos } = useMainScreen();

  return (
    <Screen>
      ...
    </Screen>
  );
}
```

다시 실행될 수 있는 상황:

- `useState` 값 변경
- Zustand store selector 값 변경
- React Query의 loading/data/error 변경
- 부모 route/layout의 렌더링
- 화면 크기 변화
- props 변경

그래서 render 중에 API 호출, 저장소 쓰기, navigation을 직접 실행하면 안 됩니다.

이런 작업은 event handler, `useEffect`, `useFocusEffect`, React Query 안에서 처리합니다.

## useEffect: mount 이후 작업

`useEffect`는 렌더링이 화면에 반영된 뒤 실행됩니다.

기본 형태:

```tsx
useEffect(() => {
  // 실행할 작업

  return () => {
    // cleanup
  };
}, [dependencies]);
```

의존성 배열:

| 형태 | 의미 |
| --- | --- |
| `[]` | mount 후 한 번 실행 |
| `[value]` | `value`가 바뀔 때마다 실행 |
| 생략 | 렌더링마다 실행. 거의 사용하지 않음 |

## SplashScreen 예시

`SplashScreen`은 화면이 mount된 뒤 세션을 복원합니다.

```tsx
const hydrate = useSessionStore((state) => state.hydrate);

useEffect(() => {
  hydrate();
}, [hydrate]);
```

읽는 법:

```text
SplashScreen이 화면에 올라온 뒤
MMKV에 저장된 세션을 Zustand store로 복원한다.
```

그 다음 launch-flow query 결과가 나오면 route를 교체합니다.

```tsx
useEffect(() => {
  if (!data) {
    return;
  }

  if (data === 'onboarding') {
    router.replace('/onboarding');
    return;
  }

  router.replace('/main');
}, [data]);
```

이 effect는 `data`가 바뀔 때마다 실행됩니다.

## useEffect cleanup

effect에서 함수를 반환하면 cleanup입니다.

```tsx
useEffect(() => {
  const timeout = setTimeout(() => {
    clearToast();
  }, 2200);

  return () => clearTimeout(timeout);
}, [clearToast, message]);
```

`ReviewToast`는 메시지가 생기면 2.2초 뒤 지우는 타이머를 만들고, 메시지가 바뀌거나 컴포넌트가 사라질 때 이전 타이머를 정리합니다.

iOS에서 timer를 invalidate하거나 observer를 remove하는 감각과 비슷합니다.

## mounted flag

비동기 작업이 끝났을 때 화면이 이미 사라졌을 수 있습니다.

그럴 때는 mounted flag 패턴을 씁니다.

`TodoWriteScreen` 예시:

```tsx
useEffect(() => {
  let mounted = true;

  (async () => {
    const existingTodos = await challengeGroupUseCase.getMyTodos(groupId, toQueryDate());
    if (mounted) {
      setTodos(...);
      setIsBootstrapping(false);
    }
  })();

  return () => {
    mounted = false;
  };
}, [challengeGroupUseCase, groupUseCase, selectedGroupId]);
```

읽는 법:

```text
화면 진입 시 기존 투두를 불러온다.
비동기 작업이 끝났을 때 화면이 아직 살아 있으면 state를 바꾼다.
화면이 사라지면 mounted를 false로 바꿔 이후 state 변경을 막는다.
```

## useFocusEffect

`useEffect`가 mount/deps 변경 중심이라면, `useFocusEffect`는 화면이 navigation stack에서 focus될 때 실행됩니다.

```tsx
useFocusEffect(
  useCallback(() => {
    // focus될 때 실행

    return () => {
      // blur될 때 실행
    };
  }, []),
);
```

iOS의 `viewWillAppear`, `viewWillDisappear`에 더 가깝게 읽을 수 있습니다.

## focus될 때 입력창 포커스

`GroupJoinScreen`은 화면에 들어오면 초대 코드 입력창에 포커스를 줍니다.

```tsx
useFocusEffect(
  useCallback(() => {
    const task = InteractionManager.runAfterInteractions(() => {
      inputRef.current?.focus();
    });
    return () => task.cancel();
  }, []),
);
```

읽는 법:

```text
화면 전환 애니메이션이 끝난 뒤
TextInput에 focus를 준다.
화면을 벗어나면 예약된 task를 취소한다.
```

Android에서는 화면 전환 중 focus를 호출하면 무시될 수 있어 `InteractionManager`로 애니메이션 이후 실행합니다.

## focus될 때 데이터 새로고침

`RankingScreen`은 화면으로 다시 돌아올 때 랭킹을 다시 불러옵니다.

```tsx
useFocusEffect(
  useCallback(() => {
    void rankingQuery.refetch();
  }, [rankingQuery]),
);
```

읽는 법:

```text
랭킹 화면이 focus될 때마다 ranking query를 다시 요청한다.
```

다른 화면에서 인증을 읽음 처리했거나 랭킹 상태가 바뀌었을 수 있기 때문입니다.

## Android 뒤로가기 제한

`useReviewScreen`은 리뷰 화면에서 Android hardware back을 막습니다.

```tsx
useFocusEffect(
  useCallback(() => {
    const subscription = BackHandler.addEventListener('hardwareBackPress', () => true);
    return () => subscription.remove();
  }, []),
);
```

읽는 법:

```text
리뷰 화면이 focus되면 hardware back listener를 등록한다.
true를 반환해서 기본 뒤로가기를 막는다.
화면이 blur되면 listener를 제거한다.
```

iOS swipe back은 `app/_layout.tsx`에서 `gestureEnabled: false`로 막습니다.

## React Query와 화면 생명주기

서버 데이터는 화면 생명주기와 별도로 React Query가 관리합니다.

예:

```tsx
const groupsQuery = useGroupsQuery();
const rankingQuery = useRankingQuery(currentGroup?.id);
```

화면이 mount되면 query hook이 실행되고, query 상태가 바뀌면 화면이 다시 렌더링됩니다.

```text
처음 render
  -> query 시작
  -> isLoading true
  -> 데이터 도착
  -> data 설정
  -> 다시 render
```

화면에서는 상태별 UI를 나눕니다.

```tsx
if (groupsQuery.isLoading || rankingQuery.isLoading) {
  return <ActivityIndicator />;
}

if (groupsQuery.isError || rankingQuery.isError) {
  return <FullScreenErrorState />;
}
```

## enabled와 화면 상태

query가 실행되려면 필요한 값이 준비되어야 합니다.

```tsx
useRankingQuery(currentGroup?.id)
```

내부:

```tsx
enabled: Boolean(groupId)
```

뜻:

```text
currentGroup이 아직 없으면 ranking query는 실행되지 않는다.
currentGroup이 생기면 query가 실행된다.
```

화면 생명주기를 읽을 때는 query가 언제 시작되는지도 함께 봐야 합니다.

## Store 변화와 화면 재렌더링

Zustand selector로 읽은 값이 바뀌면 화면이 다시 렌더링됩니다.

```tsx
const selectedGroupId = useMainStore((state) => state.selectedGroupId);
```

예:

```text
사용자가 그룹 선택
  -> mainStore.selectedGroupId 변경
  -> useMainScreen 재실행
  -> currentGroup 변경
  -> useMyTodosQuery queryKey 변경
  -> 새 그룹의 투두 조회
  -> 화면 재렌더링
```

이 흐름은 React Query와 Zustand가 함께 만드는 화면 생명주기입니다.

## useMainScreen의 보정 effect

`useMainScreen`은 서버 그룹 목록이 바뀌었을 때 선택된 그룹이 유효한지 보정합니다.

```tsx
useEffect(() => {
  if (!groupsQuery.data?.length) {
    if (selectedGroupId !== null) {
      setSelectedGroupId(null);
    }
    return;
  }

  if (!currentGroup) {
    setSelectedGroupId(groupsQuery.data[0].id);
  }
}, [currentGroup, groupsQuery.data, selectedGroupId, setSelectedGroupId]);
```

읽는 법:

```text
그룹 목록이 없으면 selectedGroupId를 null로 정리한다.
그룹 목록은 있는데 현재 선택 그룹이 유효하지 않으면 첫 번째 그룹으로 보정한다.
```

서버 데이터 변화가 store 상태를 보정하는 예입니다.

## Ref와 화면 생명주기

`useRef`는 렌더링과 별개로 값을 기억합니다.

`CertificationDetailScreen` 예:

```tsx
const thumbListRef = useRef<FlatList>(null);
const mediaScrollRef = useRef<ScrollView>(null);
const readTodoIdsRef = useRef<Set<number>>(new Set());
```

용도:

| ref | 역할 |
| --- | --- |
| `thumbListRef` | 썸네일 FlatList 위치 제어 |
| `mediaScrollRef` | 큰 이미지 ScrollView 위치 제어 |
| `readTodoIdsRef` | 이미 읽음 처리한 todo id 기억 |

`readTodoIdsRef`는 값이 바뀌어도 화면을 다시 그릴 필요가 없으므로 state가 아니라 ref가 적절합니다.

## 선택 index와 스크롤 동기화

`CertificationDetailScreen`은 선택 index가 바뀌면 썸네일과 큰 이미지 스크롤 위치를 맞춥니다.

```tsx
useEffect(() => {
  if (orderedTodos.length === 0) {
    return;
  }

  requestAnimationFrame(() => {
    thumbListRef.current?.scrollToIndex({
      index: safeIndex,
      animated: true,
      viewPosition: 0.5,
    });
    mediaScrollRef.current?.scrollTo({
      x: mediaCardWidth * safeIndex,
      animated: true,
    });
  });
}, [mediaCardWidth, orderedTodos.length, safeIndex]);
```

읽는 법:

```text
선택 index 또는 화면 너비가 바뀌면
다음 frame에서 썸네일 리스트와 미디어 스크롤 위치를 맞춘다.
```

`requestAnimationFrame`은 현재 렌더링 반영 이후 스크롤 명령을 안전하게 실행하기 위한 장치입니다.

## 읽음 처리 side effect

랭킹에서 다른 멤버 인증을 열면 현재 todo를 읽음 처리합니다.

```tsx
useEffect(() => {
  if (context.source !== 'ranking' || !currentTodo?.id || readTodoIdsRef.current.has(currentTodo.id)) {
    return;
  }

  readTodoIdsRef.current.add(currentTodo.id);

  void challengeGroupUseCase
    .readTodo(currentTodo.id)
    .then(() => {
      if (context.groupId) {
        void queryClient.invalidateQueries({ queryKey: ['ranking', context.groupId] });
      }
    })
    .catch(() => {
      readTodoIdsRef.current.delete(currentTodo.id);
    });
}, [challengeGroupUseCase, context.groupId, context.source, currentTodo?.id, queryClient]);
```

읽는 법:

```text
랭킹에서 들어온 인증 상세이고,
현재 todo id가 있고,
아직 읽음 처리하지 않았다면
readTodo API를 호출한다.
성공하면 ranking query를 무효화한다.
실패하면 ref에서 id를 제거해 나중에 다시 시도할 수 있게 한다.
```

## route guard

어떤 화면은 필요한 상태 없이 들어오면 안 됩니다.

`CompleteScreen`은 완료 payload가 없으면 `/start`로 돌려보냅니다.

```tsx
useEffect(() => {
  if (!payload && !isLeavingToMain) {
    router.replace('/start');
  }
}, [isLeavingToMain, payload]);
```

이런 코드는 route guard처럼 읽으면 됩니다.

```text
이 화면을 보여주기 위한 필수 상태가 없다면 안전한 화면으로 보낸다.
```

## 화면에서 하면 안 좋은 일

컴포넌트 함수가 실행되는 render 단계에서 직접 하면 안 좋은 일:

- API 호출
- timer 등록
- event listener 등록
- storage write
- navigation 실행
- state 변경

대신:

| 작업 | 위치 |
| --- | --- |
| 서버 조회 | React Query |
| 버튼 클릭 후 API 호출 | event handler, mutation |
| mount 후 1회 작업 | `useEffect(..., [])` |
| focus될 때 작업 | `useFocusEffect` |
| timer/listener 정리 | effect cleanup |
| navigation guard | `useEffect` |

## 화면 생명주기 읽는 순서

처음 보는 화면은 아래 순서로 읽으면 좋습니다.

```text
1. route 파일을 본다.
   -> app/*.tsx가 어떤 Screen에 연결되는지 확인

2. Screen 상단 import를 본다.
   -> useEffect, useFocusEffect, useRef, query, store 사용 여부 확인

3. useState를 본다.
   -> 화면 내부 상태 확인

4. useRef를 본다.
   -> 렌더링과 무관한 참조값 확인

5. query hook을 본다.
   -> 서버 데이터 로딩 흐름 확인

6. useEffect를 본다.
   -> mount/deps 변경 후 side effect 확인

7. useFocusEffect를 본다.
   -> 화면 focus/blur 시 작업 확인

8. early return을 본다.
   -> loading/error/empty/guard UI 확인

9. event handler를 본다.
   -> 사용자 행동 후 상태 변경/API/navigation 확인

10. cleanup을 본다.
    -> timer/listener/task가 정리되는지 확인
```

## iOS와 RN 대조표

| iOS 개념 | RN에서 가까운 개념 | Dogether 예시 |
| --- | --- | --- |
| `viewDidLoad` | `useEffect(..., [])` | Splash의 `hydrate()` |
| `viewWillAppear` | `useFocusEffect` | Ranking refetch, GroupJoin input focus |
| `viewWillDisappear` | `useFocusEffect` cleanup | BackHandler remove, task cancel |
| `deinit` | effect cleanup / unmount | timer clear, mounted false |
| `@IBOutlet` | `useRef` | TextInput, FlatList, ScrollView ref |
| async loading state | React Query | groups/ranking/todos query |
| 화면 guard | `useEffect + router.replace` | Complete payload 없으면 `/start` |
| navigation push | `router.push` | `/todo-write`, `/certify` |
| navigation replace | `router.replace` | splash 분기, 인증 성공 |

## 자주 헷갈리는 점

### useEffect가 viewDidLoad와 완전히 같나?

아닙니다. `useEffect(..., [])`는 mount 후 한 번 실행된다는 점에서 비슷하지만, React의 렌더링 모델과 dependency array를 이해해야 합니다.

### 화면이 stack에 남아 있으면 unmount되지 않을 수 있나?

네. navigation stack에 남아 있는 화면은 완전히 제거되지 않을 수 있습니다. 그래서 "다시 보일 때마다" 해야 하는 작업은 `useEffect`보다 `useFocusEffect`가 더 적절할 수 있습니다.

### refetch는 생명주기인가?

React Query 관점에서는 서버 상태 갱신입니다. 하지만 화면 focus 시점에 refetch를 호출하면 화면 생명주기와 연결된 데이터 갱신이 됩니다.

### useRef와 useState 차이는?

```text
화면에 보여줘야 해서 바뀌면 렌더링되어야 하는 값 -> useState
렌더링과 무관하게 기억만 하면 되는 값 -> useRef
```

### cleanup을 왜 해야 하나?

화면이 사라진 뒤에도 timer, listener, async task가 남아 있으면 예기치 않은 state 변경이나 메모리 누수가 생길 수 있습니다.

## 한 줄 요약

